## Renewable allowances

Defaults: `RESUME_LIMIT=10`, `INTERVIEW_LIMIT=3`, `USAGE_WINDOW_HOURS=24` in `backend/.env`. Retired `FREE_*` and `PRO_*` settings have no effect. Restart API and workers after configuration changes; run all processes with identical limits. These values do not configure SMTP or hosted Supabase Auth.

Each account has one fixed window. Its first accepted initial-processing reservation starts the window using the PostgreSQL clock, after obtaining the account lock. Both capacities renew exactly 24 hours later. Activity never extends the deadline. At expiry, reads expose full allowances with no active window; the next accepted reservation starts the next window. This is neither midnight renewal nor inactivity renewal. For example, Tuesday 14:30 first use renews Wednesday 14:30. Displayed dates use the viewer's local timezone; backend connections use UTC.

`usage_windows` and `usage_attempts` form the new durable ledger. Account row locks serialize initial reservations and retries; PostgreSQL counts reserved and consumed attempts in the current window. Account-scoped creation keys remain in `usage_reservations`. Historical reservations are preserved and excluded from the daily ledger. A duplicate creation returns its existing resource without starting a new window or retrying failed processing. Reuse with different inputs remains a conflict.

Initial analysis/question generation consumes its attempt on success and releases it on terminal failure. Intermediate automatic job retries retain their reservation. Explicit retry after failure acquires a new attempt in the current window, including after expiry. Released attempts retain their original window. A job still running at expiry settles its old attempt; it does not charge or refund the new window. Fenced job leases prevent old workers settling a newer retry. Worker failure/exhausted-lease handling now follows the same resource-before-job lock order as completion and API retry; exhausted busy resources are skipped until the next claim. Consumed attempts cannot be released by abandonment or deletion. Deleting pending resume work cancels it and releases only its pending reservation. Transcription, answers, follow-ups, evaluation, report viewing/export and resuming a session create no interview charge.

`GET /capabilities`, workspace responses and quota errors expose limits, consumed (`used`), pending (`reserved`), remaining, server time, window start and reset. The frontend shows both allowances across the workspace, refetches on server-relative expiry, focus/visibility return and reservation mutations, and polls for other-tab changes. A stale enabled button still encounters the authoritative backend check. Exhausted accounts retain saved results and sessions. Demo mode simulates 10/3 in a shared browser window; its clock/storage are explicitly simulation only, never live eligibility.

Before replacing anything, inspect the **matching configured project** in Dashboard → Authentication → Email/SMTP and Rate Limits. Preserve an existing suitable provider if present, and verify its account-specific capacity and sender activation. Documentation checked on 10 November 2026 states Supabase's default sender is restricted to organization team addresses and currently 2 emails/hour. Custom SMTP initially has a 30/hour limit; changing application environment variables does not alter it. Sources: [official SMTP setup](https://supabase.com/docs/guides/auth/auth-smtp), [official Auth limits](https://supabase.com/docs/guides/auth/rate-limits).

As researched on 10 November 2026, if no suitable provider exists, Brevo Free is an option: 300 sends/day shared with other email activity, no rollover. Its former engagement-based hourly transactional quota was removed; account suspension/activation still matters. The daily maximum is not a delivery SLA. At exhaustion, queued transactional mail can arrive too late for auth links. Sources: [free-plan limits](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan), [hourly quota removal and queues](https://help.brevo.com/hc/en-us/articles/360021917460-Why-are-emails-added-to-a-queue).
